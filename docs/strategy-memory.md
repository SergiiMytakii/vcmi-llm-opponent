# Память стратегии ExternalAI

Автоматический разбор последствий и перенос обобщённых уроков между партиями
описан отдельно: [обучение на игровом опыте](experience-learning.md). Эти уроки
не подменяют наблюдения и операционный план текущей партии.

Каждый запрос получает текущую наблюдаемую ситуацию и `memory`. Отдельные
запуски Codex продолжают переданный план. История сессий Codex не является
источником памяти партии; после перезапуска контроллера она не требуется.

## Разделение ответственности

- `memory.plan`: намерения модели — цель, стабильная ссылка на цель, причина,
  исполнитель `executor_ref`, проверяемые `ready_when`/`complete_when`,
  до четырёх следующих шагов, резерв ресурсов, условия пересмотра и оценка
  прогресса. Оценка модели не подтверждает выполнение действия.
- `memory.known_objects`: наблюдения адаптера, полученные только из доступной
  игроку информации. Запоминаются до 128 объектов/направлений разведки; текущая
  цель плана сохраняется при сокращении списка. Затем предпочтение отдаётся
  более свежим наблюдениям. Это ограниченная память, а не полный архив карты.
- `memory.recent_results`: последние восемь результатов команд адаптера.
  `completed` подтверждает постусловия строительства/найма;
  `progress_observed` означает продвижение героя, **не захват цели**;
  `unconfirmed` запрещает считать намерение выполненным.

`stale` означает старое наблюдение. `last_seen_day` не обновляется без нового
наблюдения. `not_seen_at_last_position` отмечает отсутствие объекта на снова
видимой прежней позиции, не его уничтожение. Скрытые перемещения и изменения
владельца не обновляют память. Армии противника проходят существующее
ограничение детализации наблюдений. Новые факты модель записывать не может.

Номера объектов во внешнем запросе назначаются адаптером при наблюдении объекта,
отдельно для каждого игрока. Это не глобальные номера движка: добавление объекта
за туманом войны не меняет обозначения видимых объектов. Частное соответствие
`ExternalAI.object_ids` сохраняется вместе с памятью, но не передаётся модели.
В предварительных сохранениях, созданных до этой защиты, память могла содержать
глобальные номера даже внутри текста плана. При их загрузке адаптер сбрасывает
только старую AI-память и неподтверждённое намерение, с предупреждением в логе.
Состояние игры и использованный бюджет запросов сохраняются; исходный файл не
изменяется. Современные сохранения восстанавливают память и обозначения целиком.

## Ответ модели

Запросы с `memory` добавляют поле `strategy` в JSON-схему ответа Codex.
`null` сохраняет прежний план; объект целиком заменяет его:

```json
{
  "goal": "Захватить шахту после подкрепления",
  "executor_ref": "object:7",
  "ready_when": {"kind": "day_at_least", "value": 8},
  "complete_when": {"kind": "target_owned", "value": null},
  "target_ref": "object:42",
  "rationale": "Нужна руда для следующего строительства",
  "steps": ["Нанять стрелков", "Идти к шахте"],
  "reserves": "Оставить 5 дерева",
  "reconsider_if": ["Враг угрожает нашему городу"],
  "progress": "Готовимся к найму",
  "change_reason": "Первый план по видимой шахте"
}
```

Ссылка должна быть из текущих действий, памяти наблюдений или прежнего плана;
для общей цели разрешён `null`. `object:<id>` относится к объекту этой партии,
`tile:[x,y,z]` — к направлению разведки. Ситуативный `action_id` не является
долговременной ссылкой. Каждый из пяти текстовых атрибутов ограничен 240 байтами
UTF-8; списки содержат 1–4 строки до 160 байт каждая; весь план — до 4096 байт.
Контроллер и адаптер независимо проверяют план и связь ответа с запросом.

Ответ без `strategy` остаётся допустимым для резервного завершения хода и
детерминированных контроллеров: прежний план сохраняется. Невалидный ответ
не заменяет план. Инструкция требует продолжать жизнеспособную цель и
пересматривать её по наблюдаемым причинам; это поведение модели, а не
жёсткий запрет движка выбирать другое действие.

## Сохранение и загрузка

Память находится в `playerLocalSettings._namespaces.ExternalAI.memory`,
рядом с существующими счётчиком попыток и незавершённым намерением.
Адаптер использует стандартный `saveLocalState(JsonNode)` без изменения сетевого
пакета. Обновление памяти передаётся в существующем JSON как
`{"_namespaces":{"ExternalAI":state}}`. Сервер обновляет этот namespace, сохраняя
поля интерфейса. Обычный снимок интерфейса заменяет его поля, сохраняя уже записанные
namespaces. Структура памяти в сохранениях остаётся прежней. Это устраняет
добавленное нами несовпадение формата `SaveLocalState`; реальная сетевая партия со
стандартным Windows-клиентом требует отдельной проверки.

Порядок записи:

1. Обновляет наблюдения и сохраняет память перед запросом к модели.
2. Проверяет ответ и сохраняет новый план вместе с намерением до команды.
3. Записывает подтверждённый результат и снова сохраняет состояние.

Память включается в обычное сохранение игры и принадлежит отдельному игроку.
Загрузка старого сохранения восстанавливает соответствующий ему план и
наблюдения. Незавершённая команда остаётся неподтверждённой; автоматически
повторять её нельзя. План не извлекается из общих файлов или логов, поэтому
такие файлы не переносят знания между игроками и партиями.

## Проверки

```sh
python3 -m unittest discover -s tests -p test_strategy.py -v
```

Проверяет принятие прежней цели, запрет выдуманных целей/фактов, отклонение
устаревшего ответа и всю цепочку Python-контроллера с подставным Codex CLI,
включая передачу памяти, схему ответа и резервное завершение хода.

Нативная проверка использует настоящий `JsonNode` той же сборки VCMI:

```sh
cmake -S tests/strategy-memory -B .build/strategy-memory-tests \
  -DVCMI_SOURCE_DIR="$PWD/.build/vcmi" \
  -DVCMI_LIBRARY="$PWD/.build/mac/bin/libvcmi.dylib" \
  -DBOOST_ROOT="/path/to/matching/boost"
cmake --build .build/strategy-memory-tests
ctest --test-dir .build/strategy-memory-tests --output-on-failure
```

Для Windows нужны заголовки, import library и доступная DLL соответствующей
Windows-сборки VCMI; путь выше — пример для macOS. Проверка покрывает
сериализацию и восстановление прежнего состояния, раздельные экземпляры
памяти, устаревание наблюдений, подтверждения результатов и ограничения объёма.
Это не заменяет проверку сохранения/загрузки в работающей игре.

На macOS 2026-10-04 два отдельных реальных вызова `gpt-6.1-sol`, `medium`
через подписку Codex продолжили прежнюю цель после подтверждённого найма,
затем сменили её на защиту города при явно заданной угрозе. Это синтетические
проверки передачи контекста, не оценка игровой силы. Используется существующий
[режим Codex exec с JSON-схемой](https://learn.chatgpt.com/docs/non-interactive-mode).

Полная партия с сохранением/загрузкой и Windows-проверка пока не выполнены.
Отдельный нативный тест уже подтвердил сохранение во время запроса и загрузку
в новом процессе: план и выполненная покупка восстановились, лимит продолжился
с третьего запроса, на следующий день обновился. Это детерминированная проверка
с `save_probe.py`, а не полная партия с Codex.
После интеграции память включена в отдельную developer-сборку: проверены
результаты переноса гарнизона и начальные наблюдения на парных картах.
См. [свежие проверки и ограничения](verification-land-duel-2026-10-04.md).
Установленная игра этой интеграцией не обновлялась.

## Проверяемый план, схема памяти 2

`executor_ref` — ссылка на текущего собственного героя либо `null` для общей/городской цели. Каждое условие содержит только `kind` и `value`: `unknown`/`null`, `always`/`null` (только готовность), `day_at_least`/целый день, `army_strength_at_least`/целое значение силы армии, `executor_at_target`/`null`, `target_owned`/`null`, `confirmed_action`/`build|recruit|transfer|upgrade|hire_hero`. Условия армии/позиции требуют исполнителя; позиции, владения и команды — цель. Сила является приблизительным значением существ VCMI, не прогнозом победы.

Адаптер выдаёт `memory.plan_review`: готовность и завершение `met|not_met|unknown`, `last_observed_change_day`, `unchanged_days` и статус `active`, `waiting_for_readiness`, `completed`, `infeasible` или `requires_revision`. Потеря исполнителя подтверждается только полным собственным списком. Владение проверяется по свежему видимому наблюдению; старое скрытое владение не завершает цель. Противоречие ранее выполненному условию готовности требует пересмотра. Два дня без полезного продвижения вызывают пересмотр, но ожидание заданного будущего дня не считается зацикливанием. Полезное продвижение — новый минимум оставшихся шагов известного маршрута, новый максимум силы армии исполнителя или целевого города, свежие сведения о цели или новое здание целевого города; для общей цели учитываются новые максимумы запасов ресурсов. Повторное движение туда-сюда и потеря с восстановлением прежней армии не обнуляют застой. Отсутствующий маршрут остаётся неизвестным. После обновления прежнее отслеживание инициализируется один раз, без сброса плана или бюджета. Отсчёт до роста и восстановление движения сами по себе не являются продвижением. Статус адаптера не выбирает новое действие: модель объясняет отмену, завершение или продолжение ожидания в новом плане.

Подтверждённая команда имеет монотонный `sequence`; завершение намерения учитывает только результаты после `plan_result_cursor` данного операционного плана. Изменения текста при том же исполнителе, цели и условиях не обнуляют подтверждения/прогресс. Незавершённая команда никогда не повторяется автоматически.

При загрузке схемы 1 сбрасывается только несовместимый старый `plan` и его проверка/прогресс. Наблюдения, результаты, собственные силы, приватные обозначения объектов, неподтверждённое действие и использованный бюджет решений сохраняются. Новые планы и фактологическая память восстанавливаются обычным серверным save/load отдельно для каждого игрока.

## Приоритет развития города

Текущий `controller/instructions.txt` задаёт порядок: Капитолий в одном основном городе → постепенное развитие жилищ существ и производства армии → хранилище ресурсов, где оно поддерживается → дальнейшее развитие магии → необязательные постройки. Состояние этапа определяется фактическими постройками и доступными действиями, а не записью о намерении. Под «гарнизонами» в этом порядке понимаются жилища существ; он не требует распределять основную армию по городам.

Обязательные зависимости относятся к своему целевому этапу. В стандартном ядре путь к Капитолию включает ратушу, городскую управу и замок; для управы нужны гильдия магов первого уровня, рынок и кузница. Поэтому обязательная начальная магия строится раньше хранилища ресурсов, а дальнейшее развитие магии — после него. Ограничения карты, модов, реальные стоимости и предлагаемые действия важнее стандартной цепочки. Хранилище ресурсов определяется по данным здания `resourceSilo` и его фактическому производству; оно не означает сокровищницу. Если ограничения карты блокируют этот этап, игрок продолжает доступное развитие.

Доступная приоритетная постройка обычно получает решение раньше обычной разведки и необязательного найма, даже если на этом исчерпывается бюджет решений за ход. Резервируется известная стоимость следующего необходимого шага. Срочная оборона, сохранение единственной боеспособной армии и немедленная решающая победа могут временно прервать развитие; причина должна опираться на наблюдение. Затем игрок возвращается к незавершённому этапу. Отсутствие немедленного пополнения героя не отменяет пользу будущего производства войск.

## Вспомогательные герои

При наличии сильного основного героя игрок стремится нанять ещё как минимум двух помощников для безопасного сбора ресурсов и разведки, если позволяют лимиты карты и бюджет. Основная армия остаётся у боевого героя. Сначала оплачивается доступная приоритетная постройка; помощники нанимаются по одному на оставшееся золото с резервом следующего известного шага к Капитолию и необходимых войск. Отложенный найм остаётся целью для последующего финансирования.

Действие `hire_hero` предлагает только доступных в собственном городском трактире кандидатов, когда свободно место посещающего героя, хватает золота и не превышены действующие лимиты. Адаптер повторно проверяет эти условия перед командой и подтверждает результат появлением нового собственного героя, ростом числа героев и расходом золота. Затем помощник получает отдельное действие движения, освобождающее место следующему. Сам найм не передаёт войска основного героя. При неподтверждённом результате команда автоматически не повторяется. Приключенческие трактиры и приглашение конкретного следующего кандидата этим действием не поддерживаются.
