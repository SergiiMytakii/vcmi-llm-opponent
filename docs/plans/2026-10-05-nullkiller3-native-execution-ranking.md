# Nullkiller3: нативный выбор способа исполнения стратегической цели

Дата: 2026-10-05. Проверенная база: `64e51ff` в `/Users/serhiimytakii/CodexWork/2026-10-05/vcmi-nullkiller3`. Независимый plan-review: APPROVE после уточнения native tiers. Статус: предложенный план; сохранение и независимый review не разрешают реализацию, игровые запуски или публикацию. Перед реализацией проверить актуальный HEAD и пользовательские изменения.

## Результат и граница

Одна законченная корректировка: LLM определяет цель, исполнителей, срок, стратегический приоритет и ограничения; NK2 выбирает лучший из допустимых нативных способов выполнить эту же цель. Разные расходы/движение/потери могут влиять на выбор через существующий evaluator. Более выгодная локальная задача не получает права изменить стратегическую цель.

Текущая проблема: `NativeCampaign::priority` заменяет nativeScore на `50000 + goal.priority`, поэтому допустимые способы исполнения одной цели теряют различия нативной оценки. Поправить существующий путь выбора, без нового стратегического владельца.

За рамками: освобождение blocked/waiting героев для посторонней работы, автоматическая оценка разумности стратегии, изменение резервов/риска/обороны, новый контракт модели, prompt/model tuning, специальные перемещения, чистка декларативных полей и сравнительная серия партий. Эти предложения не входят в обязательный результат. Старый общий план NK3 сохраняется; данный файл уточняет только выбор исполнения.

## Порядок работы

1. **Зафиксировать наблюдаемую ошибку выбора.** Через реальный публичный вход NK3 подать фиксированную стратегию без платной модели: одна цель и как минимум два конфликтующих нативных способа её исполнения, оба проходят нынешние проверки риска, резервов и срока. Выбрать случай, где штатная нативная оценка различает способы, но нынешний выбор этого не учитывает; проверить фактическую выбранную задачу/команду. Red должен доказывать потерю выбора, а не только отсутствие поля в классе.

2. **Вернуть нативное ранжирование внутри цели.** В существующих `choseBestTask`, `buildPlanAndFilter`, `TaskPlan::mergeAndFilter` и окончательной сортировке использовать согласованный порядок выбора. Сначала сохраняется действующее преимущество срочных задач и стратегический приоритет. При одинаковом стратегическом приоритете порядок разных целей стабилизируется их порядком в принятом плане; внутри одной цели сравнивается native rank. Для обычного прохода применимы только существующие tiers `INSTAKILL…DEFEND` в штатном порядке: первый tier с положительной оценкой определяет ранг задачи, затем сравнивается score внутри этого tier. Для городского priority pass используется только `BUILDINGS`, как в текущем `choseBestTask`; он не участвует в обычном ранжировании маршрутов. Оценки разных tiers не складываются, больший score позднего tier не вытесняет положительную оценку раннего. Оценку получить на свежем EvaluationContext до campaign override и конфликтной фильтрации; ноль в раннем tier не должен прерывать оценку последующих tiers. Нулевые оценки во всех tiers не становятся новым veto для уже допустимой стратегической задачи; при равенстве остаётся стабильный порядок.

   Ранги нужны только для текущих задач, не сериализуются и не используются после exchange/load/replan. Повторный проход не должен использовать ранее повышенный стратегический priority как native score. Обычный NK2 и задачи вне стратегии сохраняют текущую ветку. Существующие проверки допустимости и разрешение конфликтов остаются обязательными. Не ограничиваться изменением финальной сортировки после удаления альтернатив и не смешивать стратегический/native score произвольным коэффициентом.

3. **Доказать границу изменения.** Red-сценарий выбирает более высокий штатный native rank при неизменных цели/сроке/резервах; изменение порядка исходных альтернатив не меняет победителя при разных рангах. Дополнительный контроль: ранний положительный native tier побеждает больший score позднего; `BUILDINGS` не подменяет обычную оценку маршрута; более высокий стратегический приоритет побеждает локально выгодную другую цель; равные приоритеты/ранги имеют устойчивый порядок; опасный либо нарушающий резерв/срок вариант остаётся запрещённым; срочная защита сохраняет текущую позицию; одинаковые разрешённые наблюдения сохраняют выбор, включая отсутствие модели. Проверить оба пути: городской priority pass и обычное планирование с конфликтующей задачей. Нативные ранги не создают запросов LLM и после загрузки/перепланирования вычисляются заново.

4. **Завершить локальную поставку.** Изменения держать в `engine/Nullkiller3/` и воспроизводимом `engine/integration.patch`; тестовый сценарий — в существующей NK3 proof-инфраструктуре. Выполнить свежую подготовку/сборку, focused checks и финальный независимый Spec/Standards Review. Игровое доказательство — только отдельная приватная сборка/профиль и при явном разрешении запусков; прежняя отмена автоматических партий не отменяется этим планом. Без необходимого runtime proof сообщить непроверенную границу, а не завершение. Установленную игру и пользовательские сессии сохранить; commit/push/deploy требуют отдельной авторизации.

## Приёмка

Одинаковая стратегия допускает несколько способов исполнения; выбор между ними реально определяется свежей нативной оценкой до удаления конфликтующих альтернатив. Цели, их стратегический порядок, текущие защитные ограничения, baseline NK2 и частота вызовов модели сохраняют описанную границу. Наличие helper-теста или новой формулы само по себе не доказывает результат; требуется выбранная нативная задача и подтверждённое исполнение в разрешённом сценарии. Улучшение общей силы игры этим изменением не заявляется.
